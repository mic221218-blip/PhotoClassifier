## 2. E 盘概况

| 项目 | 结果 |
| --- | --- |
| 磁盘 | WD Elements SE，USB 外置 **机械硬盘（HDD）** |
| 容量 | 1TB，已用约 989GB，**剩余约 11GB** |
| 湖畔日出样本 | 1,375 个文件（701 JPG + 667 NEF + 7 MOV） |
| 建筑样本 | 854 个文件（429 JPG + 423 NEF + 1 NEV + 1 MP4） |

| 户外活动样本 | 7,204 个文件（3,664 JPG + 3,492 NEF + 46 MOV） |

结论：

- E 盘是 **USB 机械盘**，不是内置 SSD；顺序读约 150–200MB/s；
- 剩余空间只有 11GB，**模型、缓存、数据库都不应写到 E 盘**；
- 照片只读，所有临时结果放 C 盘。

## 3. 技术探测结果

样本：4 张 NEF + 4 张同组 JPG + 4 张 HEIC + 3 张手机 JPG + 2 张大 JPG。

| 类型 | 数量 | EXIF | 解码 / 预览 | RGB 输入 | 单张耗时 |
| --- | --- | --- | --- | --- | --- |
| NEF | 4 | 4/4 成功 | 4/4 提取内嵌 JPEG 成功 | 4/4 可用 | 87–102ms |
| 同组 JPG | 4 | 4/4 成功 | 4/4 成功 | 4/4 可用 | 62–74ms |
| 手机 JPG | 3 | 3/3 成功 | 3/3 成功 | 3/3 可用 | 约 19ms |
| 测试 JPG（大） | 2 | 2/2 成功 | 2/2 成功 | 2/2 可用 | 98–111ms |
| HEIC | 4 | 跳过（当前解析器不支持） | **4/4 失败** | 不可用 | 0.1–132ms |
| MOV / MP4 | — | 未处理 | 不参与 | — | — |

### HEIC 失败原因

```
UnidentifiedImageError: cannot identify image file '...HEIC'
```

当前 Pillow 没有 HEIF 解码插件，需要增加 `pillow-heif`（底层 libheif）。
手机文件夹里已有 **99 个 HEIC**，如果不补这个依赖，这部分照片无法参与内容识别。

### 当前依赖状态

| 依赖 | 状态 |
| --- | --- |
| Pillow | 已安装 12.3.0 |
| numpy | **未安装** |
| onnxruntime | **未安装** |
| pillow-heif | **未安装** |
| torch | 未安装（也不需要） |

结论：技术路线本身可行，但要先把 **numpy + onnxruntime + pillow-heif** 补齐。

## 4. 性能估算

按样本的单张解码耗时估算（只算读取 + 解码，不含模型推理）：

| 数据量 | 估算 |
| --- | --- |
| 1,375 张（湖畔日出样本） | 约 **1.5–2 分钟** |
| 7,204 张（户外活动样本） | 约 **8–10 分钟** |

这是 USB 机械盘 + 只读解码的估算，实际会在缓存命中时更快；模型推理另算。

### 重要优化：RAW+JPEG 不要重复识别

E 盘大量照片是 **NEF + JPG 同组**（同文件名、同一张照片）：

- 湖畔日出样本：667 NEF + 701 JPG；
- 户外活动样本：3,492 NEF + 3,664 JPG；
- 建筑样本：423 NEF + 429 JPG。

如果两张都跑模型，等于同一张照片算两遍，还会产生两套重复标签。

建议：

- 按“文件名 stem + 拍摄时间”配对；
- 有 JPG 时优先用 JPG（解码快、体积小）；
- 没有 JPG 时才用 NEF 内嵌预览；
- 识别结果同时写到同组的 NEF 和 JPG，只跑一次模型。

这能把 NEF+JPG 场景的推理量减少约一半。

## 5. GitHub 开源项目调研

| 项目 | 许可证 | 技术栈 | 可借鉴点 | 是否直接采用 |
| --- | --- | --- | --- | --- |
| [LibrePhotos](https://github.com/LibrePhotos/librephotos) | **MIT** | Python/Django + React；ONNX Runtime；OpenCLIP、InsightFace、场景分类 | **最接近**：ONNX、无 PyTorch、有标签/语义搜索/场景分类；Windows 有 standalone | 不直接嵌入（完整 Web 应用），借鉴架构和模型选择 |
| [Immich](https://github.com/immich-app/immich) | **AGPL-3.0** | TypeScript/NestJS + Python ML 服务；CLIP | 成熟的“照片库 + ML 服务”架构、任务队列 | 不嵌入（AGPL + 重型服务） |
| [PhotoPrism](https://github.com/photoprism/photoprism) | **AGPL-3.0 + 附加商标条款** | Go + TensorFlow；Label Models | 标签模型、索引流程、隐私优先 | 不嵌入（Go/TensorFlow，许可证限制） |
| [LimanPhotos](https://github.com/NuruNabiyev/LimanPhotos) | Apache-2.0 | Kotlin 桌面；Ollama + LLaVA | 离线桌面 + 本地视觉语言模型 | 不采用（LLaVA 太重，不适合 1 万张批量） |
| [ONNX Runtime](https://onnxruntime.ai/) | MIT | C++/Python | 本地 CPU/GPU 推理 | 采用（作为运行库） |
| [OpenCLIP](https://github.com/mlfoundations/open_clip) | 代码 MIT；权重各自许可 | PyTorch/ONNX 导出 | 零样本分类候选 | 作为 M0 对照模型 |
| pillow-heif | 需核对（含 libheif/LGPL 依赖） | Pillow 插件 | HEIC/HEIF 解码 | 需要加入，先核对许可证 |

### 调研结论

1. **没有找到一个可以直接拿来嵌入的“Python 桌面自动打标库”**；
2. 最值得参考的是 **LibrePhotos（MIT，ONNX Runtime，无 PyTorch）**，但它是完整 Web 应用，不是可复用组件；
3. Immich / PhotoPrism 都成熟，但 AGPL + 重型服务，不适合直接嵌入；
4. 合理路线仍是：**自己的小管线 + ONNX 模型 + 参考 LibrePhotos 的模型组合**；
5. 不接 API 的决定可行：模型可以完全本地运行。

> 以上许可证信息来自各项目仓库（2026-10-23）；模型权重许可证仍需逐个核对，尤其是 Places365 / CLIP / YOLO 系列。

## 6. 技术路线判断

### 可行

- NEF 内嵌预览提取成功，能产出 RGB 输入；
- JPEG 解码成功，尺寸/EXIF 正常；
- 读取、解码、RGB 预处理这条链路没有阻塞；
- 1,375 张的解码成本约 1.5–2 分钟，可以接受；
- 全本地、离线，不需要 API。

### 待补

1. **HEIC 支持**：`pillow-heif`，否则手机照片（99 个 HEIC）不可用；
2. **numpy + onnxruntime**：模型推理必需；
3. **NEF+JPG 配对去重**：否则同一张照片算两遍；
4. **模型/权重许可证核对**：Places365 / CLIP / 检测器；
5. **E 盘写入禁止**：模型、缓存、数据库全部放 C 盘。

### 不建议

- 直接部署 Immich / PhotoPrism 来“借用”识别：它们是完整服务，不是库；
- 直接把 PhotoPrism 的 TensorFlow 模型搬进来：AGPL + 额外条款；
- 用 LLaVA/Ollama 做 1 万张批量识别：太重、太慢；
- 在当前阶段跑全量 7,204 张：先用小样本验证。

## 7. 下一步建议

本次只完成了“技术管线”测试，**没有跑模型**。建议下一步按顺序：

1. 在 C 盘虚拟环境安装 `numpy`、`onnxruntime`、`pillow-heif`；
2. 用 **20–30 张**样本（NEF/JPG/HEIC 各几组）跑一个最小模型，验证：
   - HEIC 能否解码；
   - RGB 预处理是否与模型输入一致；
   - 单张推理耗时；
   - 显存/内存占用；
3. 再进入 150 张的正式评测（V3.5 计划的 M0）；
4. 全量 1,375 张放到最后，且只读 E 盘。

**当前状态：技术路线可行，但 HEIC 和依赖是必须先补的坑；AI 模型还没有开始测。**
