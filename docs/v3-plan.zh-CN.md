## 1. 目标与范围

### 1.1 一句话目标

让每张照片可以拥有**任意多个（扁平）标签**：既包括系统自动算出来的
「夜景 / 高感 / 模糊 / 重复」，也包括**用户自己创建和编辑的标签**
（建筑、天空、家人、待修……），并且能按标签组合筛选。

### 1.2 为什么 V3 必须做

V2 的规则和 V2.5 的质量标记都只是**派生结果**：它们由 EXIF / 像素实时算出来，
用户不能新增、不能改名、不能表达「这是我想要的照片」。

真实需求是：

- 「这次拍摄里，把**建筑**和**天空**的都找出来」——规则做不到；
- 「这些是**给客户**的、那些是**留着自己看**的」——只能人工标注；
- 「先粗筛一遍，把要精修的 30 张打上**待修**」——需要一个持久的标记层。

V3 就是把「用户自己的标签」补上，并让标签、规则、质量三类条件在**同一个筛选器**
里工作。它是 V4（智能筛选）和 V5（导出到 Lightroom / XMP）的数据基础。

### 1.3 范围

| 能力 | 输入 | 输出 | V3 |
| --- | --- | --- | --- |
| 标签库 | 用户输入 | `tags` 表（名称、颜色、创建时间） | ✅ |
| 打标签 | 一张 / 多张照片 | `photo_tags` 关联（幂等） | ✅ |
| 移除标签 | 照片 + 标签 | 删除关联，不删照片 | ✅ |
| 重命名 / 删除标签 | 标签 | 更新名称 / 删除全部关联 | ✅ |
| 单张编辑 | 详情面板 | chips + 输入框 + 自动补全 | ✅ |
| 批量编辑 | 结果多选 | 右键菜单 + 确认 + 单步撤销 | ✅ |
| 标签筛选 | 左栏标签列表 + 搜索 | 与规则/质量共用 AND/OR | ✅ |
| 标签展示 | 结果列 / 详情 | ★ 前缀 + 彩色 chips | ✅ |
| 标签统计 | 数据库 | 每个标签的照片数（含 0） | ✅ |
| 标签颜色 | 名称哈希 | 自动生成并持久化 | ✅ |
| 标签层级 / 分组 | — | — | ❌（V4+） |
| 自动内容标签（建筑/天空…） | — | — | ❌（V3.5） |
| 写 XMP / 写 EXIF | — | — | ❌（V5 导出时再评估） |

### 1.4 明确不做

- **不把标签写进照片文件 / 不生成 sidecar**：仍然只写 SQLite；
- **不做标签层级、标签组、同义词**：V3 标签是扁平的；
- **不做「按规则自动打用户标签」**：规则命中已经在「自动标签」里；
- **不做标签云 / 复杂统计图**：只做计数与列表；
- **不删除、不移动、不重命名原片**：与现有安全原则一致。

### 2.1 已有能力

| 模块 | 现状 | 对 V3 的影响 |
| --- | --- | --- |
| `src/database.py` | `photos`（22 列）+ `folders` + `photo_quality`；`SCHEMA_VERSION = 1`，`PRAGMA user_version` 已就位 | V3 加两张表、版本升到 `2`，纯加法迁移 |

| `src/main.py` | `scan / show / stats / classify / filter / analyze / quality / dupes`；`run_filter()` 自己实现规则+质量筛选 | V3 抽出统一筛选层，CLI 与 GUI 共用 |
| `src/gui.py` | 左栏：文件夹库 + 6 条规则 + 6 个质量标记 + GPS + AND/OR；结果表 9 列；详情面板固定底部按钮；`_passes_filter()` 自己实现筛选 | V3 增加标签区、标签编辑器、批量菜单；筛选逻辑并入统一层 |
| `tests/` | **249** 个测试全绿；GUI 在真实 Tk 窗口里测试 | V3 新增标签/筛选/迁移测试，目标 300+ |

### 2.2 现有筛选逻辑的局限

现在 GUI 与 CLI 各写了一份「规则 + 质量」的 AND/OR 判断：

- GUI：`PhotoClassifierApp._passes_filter(info, matches, quality_flags)`；
- CLI：`run_filter(...)` 里再做一遍。

V3 还要加标签条件，如果继续各写一份，会出现三份逻辑、行为不一致。
本方案会把它抽到 `src/filtering.py`，两边只负责组装条件，不再各自判断。

### 2.3 与 Word 规划的差异

| Word 里的设想 | 实际代码 | 本方案的处理 |
| --- | --- | --- |
| V3「多标签系统」只给了标签示例 | 规则/质量已经以「自动标签」形式存在 | V3 不重复造系统标签，只补**用户标签**，并统一筛选 |
| 没规定标签存哪里 | SQLite 已有 schema 版本机制 | 新增 `tags` / `photo_tags`，版本 1→2 |
| 没提标签与规则的关系 | 规则实时、不落库 | 保持「系统标签派生、用户标签存储」，避免规则结果过期 |
| 没提批量操作 | GUI 结果树默认支持多选，但没有批量动作 | V3 增加多选 + 右键批量打标签 + 确认 + 撤销 |
| 没提性能 | 1,375 张样例；设计目标 1 万张 | 标签缓存 + SQL 计数，刷新预算 ≤ 200ms |

## 3. 设计原则

1. **系统标签派生，用户标签存储。**
   规则与质量结果永远实时计算（阈值改了立即生效），不写进标签表；
   用户标签是持久数据。两者在 UI 上统一呈现、统一筛选，但不混淆来源。
2. **只写数据库。** 标签不写 EXIF、不写 XMP、不改文件；原片安全原则不变。
3. **幂等。** 同一张照片重复添加同一个标签不会产生重复关联；
   批量操作可重复执行。
4. **扁平优先。** V3 不做层级/分组；先把「一张照片多个标签」做扎实，
   层级留给 V4 的筛选表达式或更晚版本。
5. **一个筛选器。** 规则、质量、标签、GPS 进入同一个 `FilterSelection`，
   AND/OR 语义唯一，CLI 与 GUI 行为一致。
6. **批量可回退。** 批量打标签必须显示数量确认，并支持撤销最近一次操作。

## 4. 标签模型

### 4.1 名词

| 名词 | 含义 |
| --- | --- |
| **标签（tag）** | 一个可复用的名字，例如「建筑」「待修」「客户 A」 |
| **关联（assignment）** | 「某张照片拥有某个标签」，是 `photo_tags` 的一行 |
| **来源（source）** | 关联的产生方式：`user`（V3）、`model`（V3.5 视觉）、`import`（未来） |
| **种类（kind）** | 标签本身的类别：`user`（V3）、`system`、`model` |
| **系统标签** | 规则/质量计算出来的标签，**不落库**，只在运行时存在 |

### 4.2 数据模型

```sql
CREATE TABLE IF NOT EXISTS tags (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    color       TEXT,                 -- "#4c8dff"，创建时按名称生成
    kind        TEXT NOT NULL DEFAULT 'user',   -- user（V3 只有这一种）
    created_at  TEXT NOT NULL
);

-- 名称大小写不敏感唯一（ASCII）；中文不受影响
CREATE UNIQUE INDEX IF NOT EXISTS idx_tags_name ON tags (name COLLATE NOCASE);

CREATE TABLE IF NOT EXISTS photo_tags (
    path        TEXT NOT NULL,        -- 与 photos.path 一致（绝对路径）
    tag_id      INTEGER NOT NULL,
    source      TEXT NOT NULL DEFAULT 'user',
    confidence  REAL,                 -- 预留给 V3.5 模型标签
    created_at  TEXT NOT NULL,
    PRIMARY KEY (path, tag_id)
);

CREATE INDEX IF NOT EXISTS idx_photo_tags_tag ON photo_tags (tag_id);
CREATE INDEX IF NOT EXISTS idx_photo_tags_path ON photo_tags (path);
```

- **不建外键**：与 `photo_quality` 保持一致（SQLite 外键默认关闭，且当前没有
  删除照片的代码路径）；删除标签时由存储层显式删关联，事务内完成。
- **`user_version` 1 → 2**：只建新表、建索引，不动 `photos`；
  现有数据库升级时无数据搬迁。
- **体积**：10,000 张 × 5 个标签 = 50,000 行，约 3–4 MB，可忽略。
- **孤儿关联**：照片记录被移除（未来功能）或路径不存在时，
  由 `prune()` 清理 `photo_tags` 中不在 `photos` 里的行。

### 4.3 名称规则

新增 `src/tags.py`（纯函数，无 I/O），集中处理：

- 去掉首尾空白与开头的 `#`（用户输入 `#建筑` 等价于 `建筑`）；
- Unicode NFC 规范化；折叠连续空白为单个空格；
- 禁止空名称、换行/控制字符；长度上限 30 个字符；
- 重名判断用 `casefold()` 比较（入库唯一索引兜底）；
- 返回「规范化名称 + 规范化 key」，供创建/查找复用。

错误一律给中文可读提示，例如
`标签名不能为空`、`标签名过长（最多 30 个字符）`、`标签「建筑」已存在`。

### 4.4 颜色

- 创建时按名称哈希在固定色板中取色，写入 `tags.color`，之后不再变；
- 色板与现有深色主题协调（8–10 种）；
- V3 不提供手动改色；详情 chips 用该颜色描边/底色，结果列受 Treeview 限制
  只用文本（★ 前缀）。

### 4.5 重命名 / 删除语义

| 操作 | 行为 | 安全约束 |
| --- | --- | --- |
| 重命名 | 更新 `tags.name`；关联不变 | 重名冲突时拒绝；空名拒绝 |
| 删除 | 删除该标签的全部 `photo_tags`，再删 `tags` 行 | 确认框显示「将从 N 张照片移除标签」；不删照片 |
| 从照片移除 | 只删一条关联 | 单张操作不需要确认；chip 上的 × 即可 |

所有写操作在一个事务里完成；失败回滚，界面提示原因。

## 5. 功能设计

### 5.1 单张标签（详情面板）

在详情面板新增「我的标签」块（放在「质量分析」之前，用户内容优先）：

```text
我的标签
[建筑 ×] [天空 ×] [待修 ×]
[ 输入标签…            ] [添加]
```

- 已有标签显示为彩色 chip，点击 `×` 立即移除；
- 输入框支持**自动补全**：输入时在下方列出匹配的已有标签，回车/点击添加；
- 输入不存在的名称时，「添加」会创建新标签并关联（需确认一次创建）；
- 空输入、超长、重复给出内联提示，不弹大对话框；
- 添加/移除后：chips 刷新、结果列刷新、左栏计数刷新、当前筛选立即生效。

### 5.2 批量标签（结果多选）

结果表本身已支持多选（`Treeview` 默认 extended）。V3 增加：

- **右键菜单**（在结果行上）：打开图片 / 打开文件位置 / 添加标签… / 移除标签… /
  复制路径；
- 选中多张时菜单项显示数量：`添加标签…（12 张）`；
- 「添加标签…」弹窗：可选择已有标签（带搜索）或输入新标签；
  确认页明确写「将给 12 张照片添加标签「建筑」」；
- 「移除标签…」只列出**这些照片共同拥有**的标签，避免误删；
- **单步撤销**：完成批量操作后，状态栏提示「已添加｜撤销(Ctrl+Z)」；
  撤销恢复上一次批量操作的关联（只保留最近一次，内存中）。

### 5.3 标签筛选（左栏）

在左栏「质量分析」与「条件组合」之间新增「我的标签」：

- 顶部搜索框：按名称过滤标签列表；
- 列表：`☑ 建筑  128`、`☐ 天空  96`（名称 + 照片数，数量来自 SQL 计数）；
- 单击切换勾选（与文件夹库一致的交互），勾选后实时筛选；
- 列表可滚动，标签多时不挤压其他区域；
- 底部入口：「管理标签…」打开管理对话框；
- 标签被删除或重命名后，筛选状态与列表同步更新；
- 「清除筛选」同时清空标签选择。

**与现有条件的关系**：标签、规则、质量共用同一个「并且 / 或者」：

- 并且：照片必须同时满足所有已勾选条件（含多个标签）；
- 或者：满足任意一个即可。

### 5.4 展示

| 位置 | 展示方式 |
| --- | --- |
| 结果表 | 合并进现有「自动标签」列：系统标签照旧，用户标签加 `★` 前缀，用竖线分隔，例如 `夜景 · 长焦 ｜ ★建筑 · ★天空` |
| 详情面板 | 彩色 chips（可点 × 移除） |
| 左栏 | 标签名 + 数量（勾选筛选） |
| CLI `show` | 末尾追加「标签：建筑、天空」 |
| CLI `tags` | 全量统计：标签、数量、创建时间 |

不新增结果列：现有 9 列在 1660px 窗口下已接近满宽，再加一列会挤压文件名。

### 5.5 标签管理对话框

`标签管理`（Toplevel，模态）：

- 表格：名称、照片数、创建时间；
- 操作：新建、重命名、删除；
- 重命名有冲突提示；删除显示影响数量；
- 关闭后返回主窗口刷新列表与筛选。

### 5.6 预置标签

首次创建标签库时写入一组**常用标签**（只建标签，不给任何照片打标）：

`风光 / 建筑 / 夜景 / 人物 / 天空 / 水面 / 城市 / 运动 / 花卉 / 日落`

- 用户可改名、删除；
- 目的是让第一次打开「我的标签」不是空的，降低使用门槛；
- 可在设置里关掉（V3 不做设置界面，暂以常量控制）。

## 6. 筛选架构（统一筛选层）

新增 `src/filtering.py`：

```python
@dataclass(frozen=True)
class FilterSelection:
    rule_ids: frozenset[str] = frozenset()
    quality_ids: frozenset[str] = frozenset()
    tag_ids: frozenset[int] = frozenset()
    and_mode: bool = True
    gps_only: bool = False

    @property
    def is_empty(self) -> bool: ...

def matches(
    info: PhotoInfo,
    *,
    rule_hits: set[str],
    quality_hits: set[str],
    tag_hits: set[int],
    selection: FilterSelection,
) -> bool:
    """规则、质量、标签、GPS 的唯一判定入口。"""
```

- GUI 与 CLI 都改成：先算好三类命中集合，再调用 `matches()`；
- 语义：`selected = rule_ids | quality_ids | tag_ids`；
  `and_mode` 为真要求全部命中，否则任意一个；
  `gps_only` 是额外硬条件（与现在一致）；
- 空选择 = 全部通过（除非 `gps_only`）；
- V4 的数值条件（ISO ≥、焦距 ≥）会扩展 `FilterSelection` 与 `matches()`，
  不需要再改两边。

| 组合示例 | 结果 |
| --- | --- |
| `tags={建筑,天空}` + 并且 | 同时有建筑和天空 |
| `tags={建筑}` + `rules={night}` + 并且 | 夜景且建筑 |
| `tags={建筑,天空}` + 或者 | 有建筑或天空 |
| `tags={建筑}` + `quality={blurry}` + 并且 | 建筑里的模糊照片 |

## 7. CLI 设计

### 7.1 命令

| 命令 | 作用 | 主要参数 |
| --- | --- | --- |
| `tags` | 标签统计 | `--db` `--limit` |
| `tag add` | 给照片加标签（不存在则创建） | `--tag NAME`（可重复）`PATH…` 或 `--match TEXT` |
| `tag remove` | 从照片移除标签 | `--tag NAME` `PATH…` 或 `--match TEXT` |
| `tag list` | 列出照片的标签 | `PATH…` / `--match` `--tag NAME` |
| `tag rename` | 重命名标签 | `OLD NEW` |
| `tag delete` | 删除标签及其关联 | `NAME` `--yes` |
| `filter --tags` | 按标签筛选 | `--tags A,B`，与 `--rules` / `--quality` / `--or` 组合 |
| `show` | 单张信息 | 末尾追加「标签」 |

### 7.2 示例

```bash
# 给一张照片打两个标签（自动创建「建筑」「待修」）
python -m src.main tag add --tag 建筑 --tag 待修 "D:\Photos\2026\DSC_0012.NEF"

# 按文件名批量打标签（会列出命中数量并要求确认）
python -m src.main tag add --tag 建筑 --match 金鸡湖

# 查看某张照片的标签
python -m src.main tag list "D:\Photos\2026\DSC_0012.NEF"

# 夜景 + 建筑（AND），并展开命中原因
python -m src.main filter --rules night --tags 建筑 --explain

# 建筑 或 天空
python -m src.main filter --tags 建筑,天空 --or

# 标签统计 / 删除标签
python -m src.main tags
python -m src.main tag delete 待修 --yes
```

### 7.3 退出码与安全

- `0` 成功；`1` 没有匹配/没有标签；`2` 参数错误；`3` 数据库不可用（与现有一致）；
- 批量 `--match` 操作先打印「将影响 N 张」再执行；`tag delete` 无 `--yes`
  时只打印影响数量并返回 `1`；
- `tag add PATH…` 要求这些照片已在 `photos` 表里（先 `scan`）；未知路径给出
  可读提示并返回 `1`；
- 所有操作只写数据库，不触碰原片。

## 9. 性能预算

| 项目 | 目标 |
| --- | --- |
| 标签缓存加载（路径 → tag_id 集合） | 10,000 张 / 50,000 关联 ≤ 100ms |
| 勾选标签后刷新结果 | ≤ 200ms（含规则与质量判定） |
| 标签列表计数 | ≤ 50ms（SQL GROUP BY） |
| 批量添加 1,000 条关联 | ≤ 200ms（单事务） |
| 数据库增长 | 50,000 行 ≈ 3–4MB |

缓存策略：标签关联与质量测量一样，用 revision 计数失效；
标签增删改后 revision +1，不每次筛选都查库。

## 13. 风险与局限

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 左栏内容越来越多 | 小屏幕上拥挤 | 已有滚动条；标签区可折叠/搜索；必要时把三类筛选改成页签 |

## 14. 对后续版本的影响

- **V3.5 视觉识别**：模型输出的标签直接写入 `tags(kind='model')` /
  `photo_tags(source='model', confidence=…)`，不需要新表；
  界面可以用「自动标签」区分来源与置信度。
- **V4 智能筛选**：`FilterSelection` 扩展数值条件（ISO/焦距/快门），
  `matches()` 换成表达式求值即可；标签 ID 已经是稳定主键。
- **V5 Lightroom / 导出**：用户标签可映射为 XMP `dc:subject`（关键词），
  导出对话框可以「按标签建文件夹 / 只导出某些标签」；本轮不写文件。
- **V6 性能**：标签缓存与 revision 失效机制复用 V2.5 的质量缓存模式，
  大库（几万张）只加载关联，不重复查每张照片。

## 16. 实施记录与偏差（2026-10-20）

> V3 **已实现并验收**。下面是最终落地与规划的差异，避免文档与代码脱节。

### 16.1 实际模块

| 文件 | 内容 |
| --- | --- |
| `src/tags.py` | 名称规范化（NFC、去 `#`、长度、控制字符）、颜色、10 个预置标签 |
| `src/tag_store.py` | `tags` / `photo_tags` 的 CRUD、幂等添加、级联删除、计数、孤儿清理、撤销用的精确关联操作 |
| `src/filtering.py` | `FilterSelection` + `matches()`，规则/质量/标签/GPS 的唯一判定入口 |
| `src/database.py` | schema `1 → 2`，新增两张表；升级时写入预置标签 |
| `src/main.py` | `tags`、`tag add/remove/list/rename/delete`、`filter --tags`、`show` 显示标签；`run_filter` 改用统一筛选 |
| `src/gui.py` | 左栏标签搜索/勾选/计数、详情 chips 编辑器、结果列 ★、右键批量、单步撤销、标签管理 |

### 16.2 与原方案的偏差

| 项 | 原方案 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 预置标签时机 | 「首次创建标签库时」 | **schema 1→2 迁移时**写入一次 | 迁移只发生一次；用户之后删光标签不会被重新塞回来 |
| 结果列顺序 | 系统标签在前、用户标签在后 | **用户标签（★）排最前**，系统标签在后 | 列宽有限，系统标签较长时会把 ★ 挤到不可见；用户标签优先 |
| 结果列宽度 | 保持原 9 列宽 | 文件名 190→180、相机 120→110、自动标签 150→180、质量 95→90、大小 85→80 | 给 ★ 标签留出空间，总宽不变 |
| 左栏标签列表 | 列表 + 计数 | 增加**滚动条**与「搜索标签」小标题 | 10 个预置标签已超过可视高度 |
| 路径处理 | 统一 `Path.resolve()` | 写入/单点查找仍 resolve；**筛选热路径不再 resolve** | 1 万张照片时 `resolve()` 每张都查文件系统，实测多花约 2.7 秒 |
| 标签管理 | 新建/重命名/删除 | 与规划一致；未做合并/排序 | V3 保持简单 |
| 撤销范围 | 批量加/减 | 与规划一致：只保留最近一次，内存中，不跨重启 | 降低复杂度 |

### 16.3 实测

| 项目 | 结果 |
| --- | --- |
| 测试 | **325 个全绿**（V3 以来新增 76） |
| 真实库迁移 | 1,375 张照片、user_version `1 → 2`、新增 10 个预置标签、原数据不变 |
| 10,000 张 / 50,000 关联 | 缓存加载 + 路径映射 **114ms**；规则+标签筛选 **11ms**；计数 **4ms** |
| 批量写入 | 1,000 张打一个标签 **21ms**；50,000 条关联 **22ms** |
| GUI | 左栏筛选、详情 chips、批量添加/移除、Ctrl+Z 撤销、管理对话框均按 M3/M4 验证 |

### 16.4 已知局限

- 标签列表按 SQLite 的名称排序（二进制顺序），中文不是拼音序；
- 标签只能扁平，不能层级/分组；
- 撤销只有最近一次批量操作，单张 chip 的 × 不进撤销栈；
- 标签只在数据库里，Lightroom 看不到（V5 再考虑 XMP）；
- 标签管理没有「合并重复标签」功能，需要手动逐个处理。

### 16.5 P0/P1 优化记录（2026-10-20）

| 项 | 优化前 | 优化后 | 说明 |
| --- | --- | --- | --- |
| GUI 筛选刷新（1,375 行） | 约 260ms | **约 40ms** | `duplicates.info_for` 不再对每行 `Path.resolve()`；新增 `src/paths.py` 统一 key |
| CLI 筛选 10,000 张 | 多花约 2.7s | — | 同一处 resolve 去除 |

| SQLite 并发 | 未设 WAL | WAL + `busy_timeout=5000` | 分析线程写质量时主线程打标签不再容易 locked |
