## 1. 目标与范围

### 1.1 一句话目标

给每张照片补上**画面本身**的度量——清晰度、曝光、重复关系——让摄影师能筛出
"大概率拍糊了 / 曝光失误 / 同一张拍了好多遍"的照片，**仍然只读、只提示、不自动处理**。

### 1.2 为什么是 V2.5

V2 的规则只看 EXIF，回答的是"**用什么参数拍的**"；它回答不了：

- 这张 1/15s 的照片，是**故意慢门**，还是**拍糊了**？
- 这次连拍 8 张，**哪张最清楚**？剩下 7 张能不能只留一张？
- 这 300 张夜景，有没有**镜头盖没摘**的？

这些必须看像素。V2.5 是项目**第一次读取图像内容**，也是第一次引入第三方库，
因此方案要把"边界"写清楚：读什么、不读什么、失败怎么办、结果只用来做什么。

### 1.3 范围

| 能力 | 输入 | 输出 | 本阶段 |
| --- | --- | --- | --- |
| 模糊检测 | 缩略灰度图 | 清晰度分数 + 是否疑似模糊 | ✅ |
| 运动模糊检测 | 同上 + 梯度方向性 + 快门 | 是否疑似运动模糊（带方向性指标） | ✅ |
| 曝光异常 | 亮度直方图统计 | 过曝 / 欠曝（含截断比例） | ✅ |
| 黑屏 / 异常照片 | 均值 + 标准差 + 截断 | 疑似黑屏（镜头盖、全黑） | ✅ |
| 重复照片 | 精确指纹（内容哈希） | 完全相同的文件分组 | ✅ |
| 近似重复 | dHash + 拍摄时间窗 | 同一瞬间的相似照片分组 | ✅ |
| 质量结果入库 | SQLite | `photo_quality` 表，可增量重算 | ✅ |
| CLI | `analyze` / `quality` / `dupes` / `filter --quality` | 报告与筛选 | ✅ |
| GUI | Tkinter 现有界面 | 质量筛选、质量列、详情块、分析进度 | ✅ |

### 1.4 明确不做（V2.5 边界）

| 不做 | 原因 | 去向 |
| --- | --- | --- |
| RAW 完整解码 / demosaic | NEF 压缩无标准库实现，libraw 是重依赖；预览图已足够判断质量 | 未来（如确有需要） |
| 删除、移动、重命名、自动标记 | 原片安全原则；界面里也没有删除按钮 | 永久不做自动删除 |
| 写回 EXIF / 生成 sidecar | 只读原则；结果只进数据库 | 暂不做 |
| 人脸 / 内容识别（建筑、天空…） | 属于语义识别 | V3.5 |
| 镜头锐度建模、按机身校准 | 需要标定数据，收益/成本不划算 | 未来 |
| 相似照片"聚类浏览"大视图 | 交互成本高，先用筛选 + 详情成员列表 | V2.5.x / V4 |
| 视频质量分析 | 视频只记录文件信息 | 不做（保持现状） |
| 自动挑出"最佳照片"并丢弃其余 | 决定权在用户 | 永不自动 |

## 3. 设计原则

1. **测量与判定分离。** 数据库只存"测出来的数"（清晰度、亮度、哈希…），
   "是否模糊"由配置阈值实时算出来。换阈值不需要重扫、不需要重算像素——
   与 V2 规则引擎"规则不落库"是同一个思路。
2. **只读、只提示。** 质量分析不写回文件、不生成 sidecar、不移动、不删除；
   界面里不会出现"删除模糊照片"这类按钮。
3. **失败不阻塞。** 视频、无内嵌预览的 RAW、损坏文件、解码异常，
   都只记一条状态/错误，继续下一张；整个任务永远能跑完并出报告。
4. **可解释。** 每个标记都带具体数值，例如
   `清晰度 68 < 120（拉普拉斯方差，512px）`、`高光截断 21% ≥ 12%`。
5. **零依赖核心。** Pillow 只允许出现在 `src/preview.py` 里；
   其余模块（度量、判定、分组、存储、CLI、GUI）不依赖它。
6. **增量可重算。** 记录 `analyzer_version` + 文件 `mtime/size`；
   只分析新增或变更的照片；算法升级时版本号 +1 自动触发重算。

## 4. 技术方案

### 4.1 像素从哪里来（`src/preview.py`）

| 文件类型 | 像素来源 | 具体做法 | 失败处理 |
| --- | --- | --- | --- |
| NEF | **内嵌 JPEG 预览** | 遍历 IFD0 与 SubIFD（`0x014A`），找 `JPEGInterchangeFormat`(0x0201)+`JPEGInterchangeFormatLength`(0x0202)；或 `Compression=7` 的 `StripOffsets`(0x0111)+`StripByteCounts`(0x0117) 拼接 | 找不到 → `preview_source="none"`，状态"无可用预览"，不算错误 |
| JPEG | 原图 | Pillow 直接解码，`draft()` 让 libjpeg 按 1/2、1/4、1/8 缩放解码 | 解码异常 → 该张 `error`，继续 |
| PNG | 原图 | Pillow 解码后按长边 512 缩放 | 同上 |
| 视频 / 未知 | 无 | 不分析 | 计入"跳过" |

**为什么不完整解码 RAW：** NEF 的压缩格式没有标准库实现；引入 libraw / rawpy
意味着几十 MB 的二进制依赖、平台绑定，而判断"糊没糊、曝没曝、像不像"用
内嵌预览（通常 1600–6048px）完全够用，速度还快一个数量级。

**预览选择策略：** 一张 NEF 可能同时有 IFD0 的全尺寸预览和 IFD1 的缩略图。
候选按**字节数从大到小**排序，取第一个通过 `FFD8…FFD9` 校验的；
单个预览上限 32 MiB（防御异常文件）。

**速度关键：** Pillow 的 `Image.draft("L", (1024, 1024))` 会让 libjpeg
在解码阶段就降采样，24–45MP 的预览图只需解出 ~1/8 尺寸，实测通常 10–25ms；
PNG 没有 draft，解码后再缩放（截图类 PNG 本身不大）。

**方向：** 统一 `ImageOps.exif_transpose()`。NEF 内嵌预览通常已经是正的，
防御性处理；方向会影响运动模糊的方向性指标，必须转。

**安全：** `mmap` 只读打开；显式设置 `Image.MAX_IMAGE_PIXELS`
（例如 40MP 上限）；逐张捕获 `UnidentifiedImageError` /
`DecompressionBombError` / `OSError` / `MemoryError`。

### 4.2 度量定义（`src/quality.py`，纯函数、零依赖）

所有度量都在**长边 512px 的灰度图**上计算（`LANCZOS` 缩放），
保证不同像素量的机型可比、耗时稳定。

| 指标 | 计算方式 | 用途 |
| --- | --- | --- |
| `blur_score` | 3×3 拉普拉斯核滤波后的**方差** | 清晰度主指标 |
| `contrast` | 灰度**标准差** | 区分"低对比"与"真模糊"；黑屏判定 |
| `anisotropy` | Sobel 水平/垂直能量：`abs(ex - ey) / (ex + ey)` | 运动模糊的方向性 |
| `mean_lum` | 平均亮度（0–255） | 过曝 / 欠曝 / 黑屏 |
| `std_lum` | 亮度标准差 | 黑屏（纯色）判定 |
| `clip_low_frac` | 亮度 ≤ 5 的像素比例 | 暗部截断 |
| `clip_high_frac` | 亮度 ≥ 250 的像素比例 | 高光截断 |
| `dhash` | 9×8 灰度相邻比较 → 64 bit → 16 个十六进制字符 | 近似重复 |
| `quick_hash` | `sha256(size + 首 128KiB + 末 128KiB)` | 精确重复的第一道筛 |
| `content_hash` | 整文件 `sha256` | 仅当 `quick_hash` 撞车时才计算，确认"完全相同" |

**为什么不用 numpy：** 拉普拉斯核、Sobel、方差都可以用 Pillow 的
`ImageFilter.Kernel` + `ImageStat.Stat`（C 实现）完成；dHash 只有 72 个像素，
纯 Python 足够。引入 numpy 只会为了几十毫秒的差距多一个重依赖。

**为什么不用频域（FFT）模糊检测：** 同样需要 numpy；拉普拉斯方差 +
方向性能给出可解释的数值，调阈值也更直观。牺牲一点精度换来零重依赖。

### 4.3 判定规则与解释（`QualityConfig` + `QualityEngine.flags()`）

阈值全部集中在 `QualityConfig`（`frozen dataclass`，与 `RuleConfig` 同构），
默认值是**待真实样本校准的初值**，不是结论。

| 标记 | 判定条件（默认阈值） | 原因示例 |
| --- | --- | --- |
| `blurry` 模糊 | `contrast ≥ 18` 且 `blur_score < 120` | 清晰度 68 < 120（拉普拉斯方差，512px） |
| `motion_blur` 运动模糊 | 满足模糊 且 `anisotropy ≥ 0.55` | 清晰度 74，方向性 0.71；快门 1/15s 慢于 1/60s，疑似手抖/运动 |
| `overexposed` 过曝 | `mean_lum ≥ 210` 或 `clip_high_frac ≥ 12%` | 平均亮度 228 ≥ 210；高光截断 21% |
| `underexposed` 欠曝 | `mean_lum ≤ 45` 或 `clip_low_frac ≥ 25%` | 平均亮度 32 ≤ 45；暗部截断 41% |
| `black_frame` 黑屏 | `mean_lum ≤ 15` 且 `std_lum ≤ 8` | 平均亮度 4，标准差 3，暗部 99%（疑似镜头盖/全黑） |
| `duplicate` 重复 | 落在某个重复组内（见 §4.4） | 与 DSC_0012.NEF 近似（dHash 距离 5，时间差 2s） |

**互斥与优先级（避免一张照片被 4 个标记淹没）：**

1. 黑屏优先：命中 `black_frame` 时**不再**报模糊/欠曝（黑图没有"清晰度"可言）；
2. 曝光互斥：`overexposed` 与 `underexposed` 只取一个；
3. 模糊只在曝光正常（非黑屏、非严重过曝）时判定，否则无意义；
4. 其余标记可以叠加（例如"模糊 + 重复"）。

**用 EXIF 辅助解释（不改判定，只改文案）：**

- 模糊 + 快门慢于 1/60s（曝光时间 ≥ 1/60s）→ "疑似手抖或运动"；
- 模糊 + 快门快于 1/250s（曝光时间 ≤ 1/250s）→ "疑似虚焦或镜头问题"；
- 欠曝 + 命中 `night` 规则 → 附一句"夜景照片欠曝可能是有意为之"。

**已知假阳性（必须在文档里承认）：** 刻意虚化的背景、摇拍（panning）、
夜景的暗调、高调/低调人像、雪景/沙滩的高亮度，都可能被标。
所以这些结果**只用于筛选提示**，且默认阈值偏保守（宁可漏一点，少误报）。

### 4.4 重复检测（`src/duplicates.py`，纯函数）

**精确重复（内容完全一致）——两阶段：**

1. 按 `(size_bytes, quick_hash)` 分组；
2. 只有组内 ≥2 张时，才对这些候选算整文件 `content_hash`；
3. `content_hash` 相同 → 精确重复组。

这样绝大多数照片只读首尾各 128KiB，**不会为了 3000 张 RAW 把 100GB 读一遍**。

**近似重复（同一瞬间的相似画面）：**

- 条件：`dhash` 汉明距离 ≤ **8**，且拍摄时间差 ≤ **10 秒**；
- 时间取 `taken_at`，缺失时退化为 `modified_at`；
- 按时间排序后只在窗口内两两比较，复杂度 `O(n·k)`（k≈窗口内张数，通常 1–10），
  10,000 张的目标是 **< 1 秒**；
- 用并查集合并成组（允许传递闭包），组内按
  **清晰度 → 像素数 → 文件大小 → 拍摄时间** 排序，第一位标注"建议保留"
  （**只是排序建议，没有任何自动动作**）。

**为什么必须加时间窗：** 不同场景的 dHash 可能撞到阈值内（尤其是大面积天空、
纯色墙面）；只比较"同一瞬间"的连续帧，误报率会低一个量级。

**包围曝光的处理：** 同一机位不同曝光会落进近似组。组内会显示各自的
EV / 快门 / ISO，由用户判断要不要拆开。V2.5 **不做**自动区分包围曝光
（V2.5.x 可按曝光差再分子类）。

**已知局限（写进文档）：** 照片复制到别的日期/别的文件夹后，
近似重复检测不到（只有精确重复能靠内容哈希抓到）。

### 4.5 依赖策略

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **Pillow（可选依赖）** | ✅ 采用 | 成熟、纯 wheel、JPEG/PNG 解码快、支持 `draft()`、Tkinter 也能直接用 |
| 纯 Python JPEG 解码器 | ❌ | 实现复杂、慢一个数量级，维护成本高 |
| Windows WIC（ctypes） | ❌ | 平台绑定、无法跨平台测试、NEF 仍需自解析 |
| rawpy / libraw | ❌ | 为"解码整张 RAW"付出几十 MB 二进制依赖，而预览已够用 |

**落地方式：**

- 依赖文件：`requirements-quality.txt` → `pillow>=10.0,<13`；
- 只允许 `src/preview.py` 导入 Pillow（顶部 `try/except ImportError` 设标志）；
- 未安装时：`analyze` 打印安装指引并以**退出码 3** 结束；
  GUI 的"质量分析"按钮置灰，提示"需要安装 Pillow（见 README）"；
- `README` 增加"可选依赖"小节，说明**不装也能正常扫描、分类、筛选**；
- 以后若迁移 PySide6，再把依赖统一收敛到 `pyproject.toml` / `requirements.txt`。

## 5. 数据模型

新增一张表，**不动 `photos` 表**（零迁移风险）：

```sql
CREATE TABLE IF NOT EXISTS photo_quality (
    path             TEXT PRIMARY KEY,
    analyzer_version INTEGER NOT NULL,
    analyzed_at      TEXT NOT NULL,
    preview_source   TEXT NOT NULL,   -- embedded_jpeg | full_image | none
    preview_width    INTEGER,
    preview_height   INTEGER,
    blur_score       REAL,
    contrast         REAL,
    anisotropy       REAL,
    mean_lum         REAL,
    std_lum          REAL,
    clip_low_frac    REAL,
    clip_high_frac   REAL,
    dhash            TEXT,            -- 16 个十六进制字符
    quick_hash       TEXT,
    content_hash     TEXT,            -- 仅在 quick_hash 撞车时计算
    file_size        INTEGER,         -- 增量判断：上次分析时的文件大小
    file_mtime       TEXT,            -- 增量判断：上次分析时的修改时间
    error            TEXT             -- 解码/读取失败原因（成功为 NULL）
);

CREATE INDEX IF NOT EXISTS idx_quality_source ON photo_quality (preview_source);
```

**设计说明：**

- **不存结论**（不存 `is_blurry`）：阈值改动、算法微调只影响展示，不需要重算；
- `analyzer_version` 常量放在 `src/quality.py`（初始 `1`），算法定义变了就 +1，
  旧行自动失效并重算；
- **不建外键**：SQLite 默认关闭外键，且当前没有任何删除照片的代码路径；
  `analyze` 结束时顺手清理"`photos` 里已不存在"的孤儿行即可；
- 失败也留一行（`error` 非空），避免每次 `analyze` 对同一批坏文件反复重试；
- schema 版本用 `PRAGMA user_version`：当前为 0，建表后置 1，
  给 V3 的标签表留一个明确的迁移钩子；
- 体量：10,000 行约 1.5–2 MB，可忽略。


## 10. 性能预算（M1 实测校准，不达标就调）

| 项目 | 目标 |
| --- | --- |
| 单张分析（预览解码 + 8 个图像指标 + 哈希） | 中位 ≤ 25ms，P95 ≤ 60ms |
| 3,000 张（4 线程） | ≤ 2 分钟 |
| 10,000 行质量数据 + 规则 + 质量筛选刷新 | ≤ 150ms（GUI 不卡） |
| 重复分组 | 10,000 张 ≤ 1 秒 |
| 单张内存峰值 | ≤ 150MB（含一张高像素预览） |
| 数据库增长 | 10,000 行 ≈ 1.5–2MB |

**降级路径：** 若高像素（24–45MP）JPEG 预览解码超预算，按顺序尝试：
① 更大的 `draft` 降采样比；② 只取 dHash 与曝光（跳过拉普拉斯）；
③ 线程数提到 8（CPU 核心允许时）。三条都要在 M1 用真实照片测过再定。

### 11.2 合成素材（`tests/image_maker.py`）

用 Pillow 生成确定性的小图（例如 640×480；仅用于需要解码的测试层）：

- 清晰棋盘格 / 文字样张 → `blur_score` 高；
- 对同一张图做 `GaussianBlur(3)` → 分数显著低；
- 垂直/水平单向模糊 → `anisotropy` 高；
- 全黑、纯灰、过曝白、欠曝暗 → 曝光/黑屏分支；
- 同一张图缩放/重新压缩 → dHash 距离小（近似重复）；
- 字节完全复制 → 精确重复；
- 同一尺寸、不同内容的图 → 不得误判精确重复。

`tests/exif_maker.py` 扩展：`build_nef_with_preview(jpeg_bytes, *, in_subifd=False)`，
把一段真实 JPEG 塞进 TIFF 的 `0x0201/0x0202`（或 SubIFD），用于预览提取测试。

### 11.3 真实样本回归（人工，M1 必做）

- 样本：用户指定 1 个文件夹，D700 与 Z6III 各 ≥ 50 张（含连拍、夜景、虚焦废片）；
- 做法：`analyze --csv data/quality.csv` → 导出指标 → 人工标注"糊/不糊"；
- 产出：一页校准结论（阈值建议 + 典型误报截图），写进 PR 描述；
- 验收：在样本上"误报 ≤ 10%、漏报可接受"再定默认阈值。

## 14. 风险与已知局限

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 部分 NEF 没有可用的内嵌预览 | 这些照片无法分析 | 记为 `preview_source="none"`，报告里单独计数；不阻塞 |
| 刻意虚化 / 摇拍 / 夜景暗调被误标 | 用户不信任结果 | 默认阈值偏保守 + 原因里写清数值 + 与 EXIF 交叉提示 + 只提示不动作 |
| 阈值跨机型差异（高像素 vs 老机型） | 同一阈值松紧不一 | 统一缩放到 512px 灰度再算；M1 分开统计 D700 / Z6III |
| 近似重复漏检异地拷贝 | 找不到"另一个文件夹里的同一张" | 精确重复靠内容哈希兜底；文档写明局限 |
| 连拍夹带包围曝光进重复组 | 建议保留可能"选错" | 组内显示 EV/快门/ISO；不自动处理 |
| Pillow 供应链 / 安装体积 | 用户装不上或版本冲突 | 可选依赖 + 版本区间 + 缺失降级 |
| 高像素预览解码超预算 | 分析变慢 | draft 降采样、线程数、必要时只算轻量指标（见 §10） |
| 数据库只增不减 | 长期膨胀 | 孤儿行清理；体量本来就小（2MB/万张） |

## 16. 对后续版本的影响

- **V3（多标签）**：质量标记天然可以作为**系统标签**（`#模糊`、`#重复`）进入标签模型，
  与用户标签共用同一张表，不需要返工；
- **V4（智能筛选）**：`filter --quality` 的 AND/OR 组合就是 V4 条件引擎的第一次预演，
  后续把"数值条件（ISO ≥、焦距 ≥）"接进同一个求值器即可；
- **V5（导出）**：重复组的"只导出建议保留的那张"是导出对话框的一个选项，
  仍然默认复制、仍然要确认；
- **V6 / 性能**：增量分析 + `analyzer_version` 让大库（几万张）也能只算新增部分；
- **未来 RAW 全解码 / 内容识别**：`preview.py` 已经是"像素来源"的唯一入口，
  以后换成 rawpy 或换成视觉模型，上层度量/判定/存储都不用动。

- 相机：Nikon Z6III；每个 NEF 有 3 个内嵌 JPEG 候选（IFD0 约 230 KB、
  SubIFD 约 960 KB、缩略图约 340 KB），取最大的一个，尺寸 6048×4032；
- **SubIFD 遍历是必需的**：只看 IFD0 只能拿到较小的预览；
- 解码（`draft` 降到 1512×1008，再缩放到 512px）：NEF 约 17 ms，JPEG 原图
  约 60–100 ms（受 JPEG 熵解码限制）；
- 单张总耗时约 50–115 ms（含 256 KiB 首尾指纹与纯 Python 度量）。

### 17.4 已知局限（实测发现）

- 纯 Python 度量受 GIL 限制：多线程主要加速 JPEG 解码；1,368 张 81 秒可用，
  但 1 万张约 10 分钟。后续如需更快，可改为进程池（单张分析已是纯函数，接口不用变）；
- 低对比画面（晨雾、大面积天空）的拉普拉斯方差天然偏低，靠 `contrast ≥ 18`
  兜底；极低对比的虚焦仍可能漏报；
- 序列识别基于拍摄节奏，一个文件夹里同时有延时和连拍时，连拍也会被豁免；
  需要严格结果时用 `--strict`；
- 近似重复只在时间窗内比较，异地拷贝只能靠精确重复发现。
