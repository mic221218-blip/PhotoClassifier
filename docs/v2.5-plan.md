## 1. Goal and scope

### 1.1 One sentence

Add **pixel-level** measurements — sharpness, exposure, duplicates — so the
photographer can find "probably blurred / badly exposed / shot eight times" photos,
while the tool stays **read-only and advisory**.

### 1.2 Why V2.5

V2 rules only read EXIF. They answer "**with what settings**", not:

- Was this 1/15 s frame an intentional slow shutter, or just blurry?
- Of this 8-frame burst, which one is sharpest, and can the other seven go?
- Out of 300 night shots, is any of them a lens-cap black frame?

Those need pixels. V2.5 is the project's **first stage that reads image content** and
the first that introduces a third-party library, so the plan draws the boundary:
what is read, what is not, what happens on failure, and what the results may be used for.

### 1.3 Scope

| Capability | Input | Output | This stage |
| --- | --- | --- | --- |
| Blur detection | downscaled grayscale image | sharpness score + suspected blur | ✅ |
| Motion-blur detection | the above + gradient anisotropy + shutter | suspected motion blur (with anisotropy) | ✅ |
| Exposure anomalies | luminance histogram stats | over/under-exposed (with clipping ratios) | ✅ |
| Black / abnormal frames | mean + std + clipping | suspected black frame | ✅ |
| Duplicate photos | exact fingerprints (content hash) | groups of byte-identical files | ✅ |
| Near duplicates | dHash + capture-time window | similar shots from the same moment | ✅ |
| Persistence | SQLite | `photo_quality` table, incremental re-runs | ✅ |
| CLI | `analyze` / `quality` / `dupes` / `filter --quality` | reports and filtering | ✅ |
| GUI | existing Tkinter shell | quality filters, column, detail block, progress | ✅ |

### 1.4 Explicitly out of scope

| Not doing | Why | Where it goes |
| --- | --- | --- |
| Full RAW decode / demosaic | compressed NEF has no stdlib implementation; libraw is a heavy dependency; the embedded preview is enough for quality judgement | future, if ever needed |
| Delete, move, rename, auto-mark | original-safety principle; the UI has no delete button | never automatic |
| Writing EXIF / sidecar files | read-only principle; results live in the database | not planned |
| People / scene recognition | semantic recognition | V3.5 |
| Lens sharpness modelling, per-body calibration | needs calibration data, poor cost/benefit | future |
| Similar-photo group browser | high interaction cost; filter + detail list first | V2.5.x / V4 |
| Video quality analysis | videos are recorded as files only | not planned |
| Auto-pick a "best" photo and discard the rest | the decision belongs to the user | never automatic |

## 3. Design principles

1. **Measurements are stored; verdicts are derived.** The database stores only measured
   numbers (sharpness, luminance, hashes…); "is it blurry?" is computed from configurable
   thresholds at query time. Changing a threshold needs no re-scan and no pixel re-read —
   the same philosophy as V2's "rules are never stored".
2. **Read-only and advisory.** Quality analysis never writes back, never creates sidecars,
   never moves or deletes; the UI will not gain a "delete blurry photos" button.
3. **Failures never block.** Video, RAW without a preview, corrupt files and decode errors
   each record a status/error and the run continues to a complete report.
4. **Explainable.** Every flag carries numbers, e.g.
   `sharpness 68 < 120 (Laplacian variance, 512px)` or `highlight clipping 21% ≥ 12%`.
5. **Zero-dependency core.** Pillow is allowed only in `src/preview.py`; metrics,
   verdicts, grouping, storage, CLI and GUI do not import it.
6. **Incremental and recomputable.** Store `analyzer_version` + file `mtime/size`;
   analyse only new or changed photos; bump the version to invalidate everything.

## 4. Technical design

### 4.1 Where pixels come from (`src/preview.py`)

| File type | Pixel source | How | Failure handling |
| --- | --- | --- | --- |
| NEF | **embedded JPEG preview** | walk IFD0 and SubIFDs (`0x014A`) for `JPEGInterchangeFormat` (0x0201) + `JPEGInterchangeFormatLength` (0x0202); or `Compression=7` with `StripOffsets` (0x0111) + `StripByteCounts` (0x0117), concatenated | none found → `preview_source="none"`, status "no preview", not an error |
| JPEG | the file itself | Pillow decode with `draft()` so libjpeg downsamples during decoding | decode error → `error` for that photo, continue |
| PNG | the file itself | Pillow decode, then scale to 512px long edge | same |
| Video / unknown | none | not analysed | counted as "skipped" |

**Why not full RAW decode:** compressed NEF has no stdlib implementation; libraw/rawpy
is a tens-of-MB binary dependency with platform bindings, while the embedded preview
(typically 1600–6048px) is more than enough to judge blur, exposure and similarity —
and is an order of magnitude faster.

**Preview selection:** a NEF may carry a full-size preview in IFD0 and a thumbnail in IFD1.
Candidates are sorted by **byte length descending**; take the first that validates as
`FFD8…FFD9`; cap a single preview at 32 MiB.

**Speed:** `Image.draft("L", (1024, 1024))` makes libjpeg decode at 1/2, 1/4 or 1/8 scale,
so a 24–45MP preview usually costs 10–25ms. PNG has no draft, so decode then resize
(screenshots are small anyway).

**Orientation:** always `ImageOps.exif_transpose()`. NEF previews are usually already
upright, but orientation affects the motion-blur anisotropy axis, so it must be applied.

**Safety:** `mmap` read-only; an explicit `Image.MAX_IMAGE_PIXELS` cap (e.g. 40MP); per-photo
handling of `UnidentifiedImageError` / `DecompressionBombError` / `OSError` / `MemoryError`.

### 4.2 Measurements (`src/quality.py`, pure and dependency-free)

Every measurement is computed on a **512px-long-edge grayscale** image (`LANCZOS`),
so bodies with different pixel counts are comparable and cost stays flat.

| Metric | Computation | Purpose |
| --- | --- | --- |
| `blur_score` | **variance** after a 3×3 Laplacian kernel | primary sharpness metric |
| `contrast` | grayscale **standard deviation** | distinguish "low contrast" from "truly blurry"; black-frame |
| `anisotropy` | Sobel horizontal/vertical energy: `abs(ex - ey) / (ex + ey)` | directionality of motion blur |
| `mean_lum` | mean luminance (0–255) | over/under-exposure, black frame |
| `std_lum` | luminance std | black frame (flat colour) |
| `clip_low_frac` | fraction of pixels ≤ 5 | shadow clipping |
| `clip_high_frac` | fraction of pixels ≥ 250 | highlight clipping |
| `dhash` | 9×8 grayscale adjacent comparison → 64 bits → 16 hex characters | near duplicates |
| `quick_hash` | `sha256(size + first 128KiB + last 128KiB)` | first exact-duplicate filter |
| `content_hash` | full-file `sha256` | computed only when `quick_hash` collides |

**Why no numpy:** the Laplacian kernel, Sobel and variance all run through Pillow's
`ImageFilter.Kernel` + `ImageStat.Stat` (C code); dHash touches 72 pixels, so plain
Python is fine. numpy would add a heavy dependency for tens of milliseconds.

**Why no FFT-based blur detection:** also needs numpy; Laplacian variance plus
directionality yields explainable numbers that are easier to tune. A little accuracy
for zero extra dependencies.

### 4.3 Verdicts and explanations (`QualityConfig` + `QualityEngine.flags()`)

All thresholds live in `QualityConfig` (a `frozen dataclass`, same shape as `RuleConfig`).
Defaults are **provisional values pending calibration on real samples**, not conclusions.

| Flag | Condition (default thresholds) | Example reason |
| --- | --- | --- |
| `blurry` | `contrast ≥ 18` and `blur_score < 120` | sharpness 68 < 120 (Laplacian variance, 512px) |
| `motion_blur` | blurry and `anisotropy ≥ 0.55` | sharpness 74, anisotropy 0.71; shutter 1/15s slower than 1/60s — suspected shake/motion |
| `overexposed` | `mean_lum ≥ 210` or `clip_high_frac ≥ 12%` | mean luminance 228 ≥ 210; highlight clipping 21% |
| `underexposed` | `mean_lum ≤ 45` or `clip_low_frac ≥ 25%` | mean luminance 32 ≤ 45; shadow clipping 41% |
| `black_frame` | `mean_lum ≤ 15` and `std_lum ≤ 8` | mean 4, std 3, shadow clipping 99% (suspected lens cap / all black) |
| `duplicate` | member of a duplicate group (§4.4) | near DSC_0012.NEF (dHash distance 5, 2s apart) |

**Mutual exclusion and priority (so one photo is not buried in four flags):**

1. black frame wins: when `black_frame` fires, do **not** report blur/underexposure
   (a black frame has no meaningful sharpness);
2. over- and under-exposure are mutually exclusive;
3. blur is only judged on normally exposed photos;
4. all other flags may stack (e.g. "blurry + duplicate").

**EXIF used for wording only (never for the verdict):**

- blurry + shutter slower than 1/60s (exposure ≥ 1/60s) → "suspected shake or motion";
- blurry + shutter faster than 1/250s (exposure ≤ 1/250s) → "suspected focus miss or lens issue";
- underexposed + `night` rule matched → append "night shots are often intentionally dark".

**Known false positives (must be documented):** intentional bokeh, panning,
low-key night scenes, high-key portraits, snow/beach brightness. This is why results are
**advisory**, thresholds default conservative (prefer a few misses over many false alarms).

### 4.4 Duplicate detection (`src/duplicates.py`, pure functions)

**Exact duplicates (byte-identical), two stages:**

1. group by `(size_bytes, quick_hash)`;
2. only for groups with ≥ 2 members compute a full-file `content_hash`;
3. identical `content_hash` → exact duplicate group.

So almost every photo costs only the first and last 128KiB — **no 100GB read for 3000 RAWs**.

**Near duplicates (similar frames from the same moment):**

- condition: `dhash` Hamming distance ≤ **8** and capture-time delta ≤ **10 s**;
- time from `taken_at`, falling back to `modified_at`;
- sort by time and compare only inside the window: `O(n·k)` (k≈frames within the window,
  typically 1–10), target **< 1s for 10,000 photos**;
- union-find merges groups (transitive closure allowed); group members are sorted by
  **sharpness → pixel count → file size → capture time**, with the first marked
  "suggested to keep" (**ordering advice only, no automatic action**).

**Why the time window is mandatory:** different scenes can collide within the dHash
threshold (large skies, flat walls); comparing only the same moment cuts false positives
by an order of magnitude.

**Bracketed exposures:** same-tripod different-exposure shots land in one near-duplicate
group. The group shows each frame's EV / shutter / ISO and the user decides. V2.5 does
**not** auto-separate brackets (V2.5.x may sub-type them by exposure difference).

**Known limitation (documented):** a copy moved to another date/folder escapes near-duplicate
detection; only exact duplicates are caught by content hash.

### 4.5 Dependency strategy

| Option | Verdict | Why |
| --- | --- | --- |
| **Pillow (optional)** | ✅ chosen | mature, wheel-only, fast JPEG/PNG, `draft()` support, usable by Tkinter too |
| pure-Python JPEG decoder | ❌ | complex, an order of magnitude slower, high maintenance |
| Windows WIC via ctypes | ❌ | platform-bound, untestable across platforms, still no NEF |
| rawpy / libraw | ❌ | tens of MB of binaries to decode full RAW that we do not need |

**Concretely:**

- dependency file: `requirements-quality.txt` → `pillow>=10.0,<13`;
- only `src/preview.py` may import Pillow (`try/except ImportError` at the top);
- when missing: `analyze` prints installation guidance and exits with **code 3**;
  the GUI's "Quality analysis" button is disabled with an explanatory hint;
- `README` gains an "optional dependency" section stating that scanning, classifying and
  filtering work without it;
- when PySide6 migration happens, dependencies move to `pyproject.toml` / `requirements.txt`.

## 5. Data model

One new table; **`photos` is untouched** (zero migration risk):

```sql
CREATE TABLE IF NOT EXISTS photo_quality (
    path             TEXT PRIMARY KEY,
    analyzer_version INTEGER NOT NULL,
    analyzed_at      TEXT NOT NULL,
    preview_source   TEXT NOT NULL,   -- embedded_jpeg | full_image | none
    preview_width    INTEGER,
    preview_height   INTEGER,
    blur_score       REAL,
    contrast         REAL,
    anisotropy       REAL,
    mean_lum         REAL,
    std_lum          REAL,
    clip_low_frac    REAL,
    clip_high_frac   REAL,
    dhash            TEXT,            -- 16 hex characters
    quick_hash       TEXT,
    content_hash     TEXT,            -- only computed on quick_hash collisions
    file_size        INTEGER,         -- incremental check: size at last analysis
    file_mtime       TEXT,            -- incremental check: mtime at last analysis
    error            TEXT             -- decode/read failure (NULL on success)
);

CREATE INDEX IF NOT EXISTS idx_quality_source ON photo_quality (preview_source);
```

**Rationale:**

- **no verdict columns** (`is_blurry` etc.): threshold or algorithm tweaks only affect
  presentation, never require recomputation;
- `analyzer_version` lives in `src/quality.py` (starts at `1`); bump it whenever a metric
  definition changes so old rows invalidate and recompute;
- **no foreign key**: SQLite has FKs off by default and there is no delete path for photos
  today; `analyze` prunes orphan rows whose path no longer exists;
- failures keep a row (`error` non-null) so repeated `analyze` runs do not retry the same
  broken files every time;
- schema version via `PRAGMA user_version`: currently 0 → create the table → set 1,
  giving V3's label tables a clear migration hook;
- size: 10,000 rows ≈ 1.5–2 MB, negligible.

## 6. Modules and dependency direction

```text
src/preview.py        ← the only module allowed to import Pillow; NEF preview / JPEG / PNG
src/quality.py        ← pure measurements + verdicts (QualityConfig / QualityMeasurement / QualityEngine)
src/duplicates.py     ← pure grouping (exact + near), no I/O
src/quality_store.py  ← photo_quality persistence (sqlite3), no business verdicts
src/database.py       ← single source of schema (photo_quality + user_version)
src/main.py           ← CLI: analyze / quality / dupes, filter --quality
src/gui.py            ← quality filters, quality column, detail block, analyse button + progress
tests/image_maker.py  ← synthetic images (sharp/blurred/over/under/black/near-dupe) + NEF with preview
```

**Dependency direction (no cycles):**

```text
main.py / gui.py
      │
      ├──> quality.py ──> formatting.py
      ├──> duplicates.py
      ├──> quality_store.py ──> database.py ──> photo_info.py
      └──> preview.py ──> (Pillow, optional)

exif_reader.py ──> photo_info.py        # quality never imports exif_reader
```

**The only change to existing code — `exif_reader.py`:**

add a public `iter_tiff_ifds(data, *, include_subifds=False)` that reuses the existing
`_parse_ifd` / `_read` and exposes IFD-chain walking (optionally following SubIFDs).
**The existing field-extraction path stays exactly as it is.** SubIFD walking gets its own
tests, and the existing 160 tests must stay green — that is the acceptance criterion for
this refactor.

## 7. Data flow

```text
scan (V1, existing)
  │  photos table (EXIF / file info)
  ▼
quality analysis `analyze` (new, explicitly triggered)
  │  preview.py: NEF embedded JPEG / JPEG / PNG → 512px grayscale
  │  quality.py: 8 image measurements + hashes
  │  quality_store.py: write photo_quality (batches of 50)
  ▼
query time (CLI / GUI)
  │  QualityEngine.flags(measurement, info)  → flags + reasons (derived live)
  │  DuplicateFinder.find(measurements)      → duplicate groups (on demand, GUI-cached)
  ▼
filtered view (rules + quality + AND/OR)
  │
  ▼
reveal in Explorer / copy path (V1.5, existing) → export (V5)
```

The originals are read-only throughout; quality results are just another set of attributes.

## 9. GUI design

The layout stays; changes are additive in three places:

| Area | Now | V2.5 |
| --- | --- | --- |
| Left filter panel | 6 rule checkboxes + GPS + AND/OR + clear | new "Quality analysis" section: **blurry / motion blur / overexposed / underexposed / black frame / duplicate** (2 columns × 3 rows), sharing the same AND/OR |
| Result table | 8 columns | new "Quality" column (~110px) with compact text such as `blurry·dup`; empty when clean; error rows stay orange |
| Detail panel | full EXIF + "Rule matches" | new "Quality analysis" block: sharpness, contrast, mean luminance, clipping, duplicate group (with members); "not analysed" hint when empty |
| Toolbar | Start scan | new "Quality analysis" button (secondary style) with a confirmation dialog explaining "only unanalysed/changed photos; read-only" |
| Progress view | shown while scanning | **reused**: title "Analysing quality", `analysed / total · %`, current file, cancellable |
| Status bar | scan summary + database path | append `quality: 2,846 analysed / 154 pending · suspected blur 287 · 12 duplicate groups` |

**Interaction details:**

- scan and quality analysis never run simultaneously (buttons disable each other);
- analysis runs in a background thread with `ThreadPoolExecutor(4)`; the UI thread only
  consumes queue messages;
- SQLite writes happen on the main thread in batches of 50 (no cross-thread writes);
- when analysis finishes, refresh results and status bar and keep the current selection;
- no duplicate tree browser in V2.5 (V2.5.x); use the "duplicate" filter + detail member list;
- extend `--selftest`: build the window, assert the quality checkboxes exist, toggle one and
  verify the row count changes.

## 10. Performance budget (verified in M1, adjusted if missed)

| Item | Target |
| --- | --- |
| Per photo (preview decode + 8 image metrics + hashes) | median ≤ 25ms, P95 ≤ 60ms |
| 3,000 photos (4 workers) | ≤ 2 minutes |
| Refresh with 10,000 quality rows + rules + quality filters | ≤ 150ms (UI stays smooth) |
| Duplicate grouping | 10,000 photos ≤ 1s |
| Peak memory per photo | ≤ 150MB (including one high-resolution preview) |
| Database growth | 10,000 rows ≈ 1.5–2MB |

**Fallback order if high-resolution (24–45MP) preview decoding misses the budget:**
① larger `draft` downscale; ② compute only dHash + exposure (skip Laplacian);
③ raise worker count to 8 where cores allow. All three must be measured in M1 on real photos.

## 11. Test plan

### 11.1 Layers

| Layer | Test points | Needs Pillow |
| --- | --- | --- |
| Metrics (`quality.py`) | grayscale arrays built in pure Python: sharp checkerboard vs Gaussian-blurred, black, flat colour, over/under-exposed gradients; assert ordering and threshold boundaries | no |
| Verdicts (`QualityEngine`) | each flag: hit / miss / boundary; exclusion priority; reason text contains numbers; config overrides | no |
| Duplicates (`duplicates.py`) | same hash → one group; distance-8 boundary; time window boundary (10s yes / 11s no); same hash far apart → no group; transitive closure; empty input | no |
| Preview (`preview.py`) | synthetic NEF with IFD0 preview; NEF with SubIFD preview; NEF without preview; normal JPEG/PNG; truncated/corrupt → error, no exception; orientation | yes |
| Store (`quality_store.py`) | idempotent upsert; version invalidation; `--force`; failure rows kept; orphan pruning; `user_version` migration | no |
| CLI | `analyze` report fields; `--csv`; `quality` / `dupes` output; `filter --quality` AND/OR; exit codes 0/1/2/3 | partly |
| GUI | quality checkboxes exist; toggling changes rows; combines with rules under AND/OR; buttons disabled during analysis; `--selftest` passes | no |
| Performance | filter refresh with 1,000 quality rows; throughput on 50 real photos (recorded manually) | yes |

### 11.2 Synthetic fixtures (`tests/image_maker.py`)

Deterministic small images (e.g. 640×480) generated with Pillow (used only by the decoding-dependent test layers):

- a sharp checkerboard / text-like sample → high `blur_score`;
- `GaussianBlur(3)` of the same image → clearly lower;
- one-directional blur → high `anisotropy`;
- all black, flat grey, blown white, dark → exposure/black-frame branches;
- downscaled/recompressed copy → small dHash distance (near duplicate);
- byte-for-byte copy → exact duplicate;
- same dimensions, different content → must not be treated as exact duplicates.

`tests/exif_maker.py` gains `build_nef_with_preview(jpeg_bytes, *, in_subifd=False)`,
embedding a real JPEG at `0x0201/0x0202` (or in a SubIFD) for preview-extraction tests.

### 11.3 Real-sample regression (manual, required in M1)

- sample: one folder chosen by the user, ≥ 50 frames each from the D700 and Z6III
  (including bursts, night shots, and out-of-focus rejects);
- procedure: `analyze --csv data/quality.csv` → dump metrics → label "blurry / not blurry" by hand;
- output: a one-page calibration note (threshold recommendation + typical false positives);
- acceptance: ≤ 10% false positives on the sample before defaults are frozen.

## 14. Risks and known limitations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Some NEFs have no usable embedded preview | those photos cannot be analysed | record `preview_source="none"`, report separately, do not block |
| Intentional bokeh / panning / dark night scenes flagged | users stop trusting results | conservative defaults + numeric reasons + EXIF cross-hints + advisory only |
| Thresholds differ across bodies (high-MP vs older) | one threshold is too tight or too loose | everything measured at 512px; M1 reports D700 and Z6III separately |
| Near duplicates missed when copied elsewhere | "the same photo in another folder" is not found | exact duplicates are covered by content hash; limitation documented |
| Bracketed exposures mixed into duplicate groups | "suggested keep" may be wrong | group shows EV/shutter/ISO; no automatic action |
| Pillow supply chain / install size | users cannot install or hit version conflicts | optional + version range + graceful degradation |
| High-resolution preview decoding exceeds budget | analysis gets slow | draft downscale, worker count, light-metrics fallback (§10) |
| Database only grows | long-term bloat | orphan pruning; the data is tiny anyway (2MB per 10k photos) |

## 16. Impact on later versions

- **V3 (multi-label)**: quality flags can become **system labels** (`#blurry`, `#duplicate`)
  in the same label model as user labels — no rework;
- **V4 (smart filtering)**: `filter --quality` with AND/OR is the first rehearsal of the V4
  condition engine; numeric conditions (ISO ≥, focal ≥) then plug into the same evaluator;
- **V5 (export)**: "export only the suggested keep from each duplicate group" becomes an
  option in the export dialog — still copy-only and still confirmed;
- **V6 / performance**: incremental analysis + `analyzer_version` keeps large libraries
  (tens of thousands) cheap;
- **future RAW decode / content recognition**: `preview.py` is the single entry point for
  pixels, so swapping in rawpy or a vision model leaves metrics, verdicts and storage untouched.

### 17.1 M0 preview feasibility (real footage)

- Sample: `D:\2026.07.13 金鸡湖日出`, 1,375 files (667 NEF + 701 JPEG + 7 MOV, 17.9 GB);
- Camera: Nikon Z6III. Each NEF has three embedded JPEG candidates (IFD0 ~230 KB,
  SubIFD ~960 KB, thumbnail ~340 KB); the largest is 6048×4032;
- **Walking SubIFDs is mandatory**: IFD0 alone only yields the smaller preview;
- Decoding (`draft` to 1512×1008, then resized to 512px): ~17 ms per NEF,
  ~60–100 ms per JPEG (entropy decoding dominates);
- ~50–115 ms per photo end to end, including the 256 KiB fingerprint and the
  pure-Python metrics.

### 17.4 Known limitations (found in practice)

- Pure-Python metrics are GIL-bound: threads mainly speed up JPEG decoding.
  81 s for 1,368 photos is acceptable, but 10,000 photos take ~10 minutes. A
  process pool can be added later without changing the interface (per-photo
  analysis is already a pure function);
- Low-contrast scenes (morning haze, large skies) naturally score low on
  Laplacian variance; the `contrast ≥ 18` guard helps, but extremely
  low-contrast out-of-focus frames can still be missed;
- Sequence detection is rhythm-based: a folder mixing timelapse and bursts will
  exempt the bursts too. Use `--strict` when strict results matter;
- Near duplicates are only compared within the time window; copies moved to
  another date/folder are only found by exact-duplicate detection.
